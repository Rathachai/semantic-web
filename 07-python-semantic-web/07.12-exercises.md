### Exercise 1: เลือกและสำรวจ open dataset

**โจทย์**

เลือก **open dataset จริงที่เป็น CSV** จากแหล่งใดแหล่งหนึ่ง

| แหล่ง | URL | ตัวอย่าง dataset |
| --- | --- | --- |
| data.go.th | `data.go.th` | สถานพยาบาล, โรงเรียน, คุณภาพอากาศ |
| data.gov | `catalog.data.gov` | สนามบิน, สถิติประชากร |
| EU Open Data | `data.europa.eu` | สถิติพลังงาน, การขนส่ง |
| Kaggle | `kaggle.com/datasets` | อะไรก็ได้ที่เป็น CSV |
| World Bank | `data.worldbank.org` | ตัวชี้วัดเศรษฐกิจ |

**ข้อกำหนดของ dataset**

- มีอย่างน้อย **200 แถว** และ **6 คอลัมน์**
- มีอย่างน้อย **2 entity ที่แยกได้** (เช่น โรงเรียน + จังหวัด)
- มีคอลัมน์ที่เป็น **ตัวเลข** อย่างน้อย 1 คอลัมน์
- มีคอลัมน์ที่เป็น **วันที่** หรือ **ปี** อย่างน้อย 1 คอลัมน์
- มี **ค่าว่าง** อย่างน้อย 1 คอลัมน์ (ถ้าไม่มี ให้ลบค่าออกเองบางส่วน)

### Exercise 2: ออกแบบ ontology และ IRI scheme

**โจทย์**

1. ออกแบบ **ontology เล็ก ๆ** สำหรับ dataset ที่เลือก โดย **reuse vocabulary มาตรฐาน** ให้มากที่สุด

| ควร reuse | ใช้กับ |
| --- | --- |
| `schema:` | `schema:School`, `schema:name`, `schema:address` |
| `geo:` | `geo:lat`, `geo:long` |
| `dcterms:` | `dcterms:identifier`, `dcterms:created` |
| `foaf:` | `foaf:name`, `foaf:homepage` |
| `skos:` | หมวดหมู่ |

2. สร้าง term ของตัวเองเฉพาะที่จำเป็น พร้อม `rdfs:subClassOf` / `rdfs:subPropertyOf` เชื่อมกลับมาตรฐาน

3. ออกแบบ **IRI scheme** ตามหลักใน [07.08](07.08-pandas-rdf.md)

**สิ่งที่ต้องส่ง**

ไฟล์ `ontology.ttl` และตาราง IRI design:

| Entity | IRI pattern | ตัวอย่าง | Business key |
| --- | --- | --- | --- |
| School | `ex:school/{school_id}` | `ex:school/10120001` | `school_id` |
| Province | `ex:province/{slug}` | `ex:province/bangkok` | `province` |
| District | `ex:district/{prov}-{dist}` | `ex:district/bangkok-bang-rak` | composite |

พร้อมตอบคำถาม:

- ทำไมจึงเลือก key นี้ และจะเกิดอะไรขึ้นถ้าใช้ auto-increment แทน
- term ไหนที่สร้างเองและทำไม reuse ไม่ได้

### Exercise 3: เขียน ETL pipeline

**โจทย์**

เขียน `my_etl.py` ที่ทำครบ 6 ขั้นตามแบบ [`etl_pipeline.py`](../code/ch07/etl_pipeline.py)

| ขั้น | ต้องมี |
| --- | --- |
| **1. EXTRACT** | อ่าน CSV ด้วย `keep_default_na=False`, รายงานคุณภาพข้อมูล |
| **2. TRANSFORM** | slugify IRI, ระบุ datatype ครบ, ข้ามค่าว่าง, reify n-ary relation ถ้ามี |
| **3. VALIDATE** | SHACL shape อย่างน้อย 5 constraint |
| **4. ENRICH** | โหลด ontology + รัน `owlrl` |
| **5. LOAD** | เขียนไฟล์ Turtle + (ถ้าทำได้) โหลดเข้า Fuseki |
| **6. QUERY** | SPARQL ตรวจผลอย่างน้อย 5 query |

**SHACL constraint ที่ต้องมี** (อย่างน้อย 5 แบบต่างกัน)

```turtle
# 1) cardinality
sh:property [ sh:path ex:schoolId ; sh:minCount 1 ; sh:maxCount 1 ] ;
# 2) datatype
sh:property [ sh:path ex:studentCount ; sh:datatype xsd:integer ] ;
# 3) value range
sh:property [ sh:path geo:lat ; sh:minInclusive -90.0 ; sh:maxInclusive 90.0 ] ;
# 4) pattern
sh:property [ sh:path ex:schoolId ; sh:pattern "^[0-9]{8}$" ] ;
# 5) class
sh:property [ sh:path ex:locatedIn ; sh:class ex:Province ] ;
# 6) sh:sparql (โบนัส)
```

### Exercise 4: Visualize เป็นกราฟ interactive

**โจทย์**

1. แปลง RDF graph → networkx แล้ววิเคราะห์:
   - node ที่มี degree สูงสุด 10 อันดับ
   - betweenness centrality
   - จำนวน connected component
   - **ตรวจ cycle ใน `rdfs:subClassOf`**
2. **กรอง `rdf:type` ออก** ก่อนหาเส้นทาง แล้วเทียบผลกับตอนไม่กรอง
3. ดึง **subgraph รอบ node ที่น่าสนใจ 1 ตัว** ในรัศมี 2 hop
4. สร้าง **pyvis HTML** ที่:
   - ใช้สีต่างกันตามชนิด node (class / individual / literal)
   - ขนาด node ตาม degree
   - มี tooltip แสดง IRI เต็ม
   - `cdn_resources="in_line"` เพื่อเปิด offline ได้
5. สร้าง **graphviz diagram** ของ class hierarchy

### Exercise 5: ให้บริการเป็น Linked Data API

**โจทย์**

สร้าง `my_api.py` ด้วย FastAPI ที่มี:

1. **`GET /`** — หน้าแรกลิสต์ entity ทั้งหมด
2. **`GET /resource/{id}`** — dereference พร้อม **content negotiation** ครบ 5 format
   (HTML, Turtle, JSON-LD, RDF/XML, N-Triples)
3. **`GET /data/{id}.{ext}`** — ระบุ format ผ่านนามสกุล
4. **`GET|POST /sparql`** — SPARQL endpoint ที่มี security guard
5. **`GET /void`** — VoID description
6. **`GET /search?q=`** — ค้นหาด้วย `rdfs:label`

**Security ที่ต้องมี**

- [ ] ห้าม UPDATE keyword ใน query endpoint
- [ ] บังคับ `LIMIT` ถ้า query ไม่มี
- [ ] timeout 30 วินาที
- [ ] rate limiting
- [ ] `Vary: Accept` header
- [ ] CORS

**Expected output**

```bash
curl -s http://localhost:8000/health | jq
```

```json
{"status": "ok", "triples": 21458, "subjects": 2252, "source": "schools.ttl"}
```

```bash
for accept in "text/turtle" "application/ld+json" "text/html" "application/rdf+xml"; do
  code=$(curl -s -o /dev/null -w "%{http_code}" -H "Accept: $accept" \
    http://localhost:8000/resource/school%2F10120001)
  ctype=$(curl -s -D- -o /dev/null -H "Accept: $accept" \
    http://localhost:8000/resource/school%2F10120001 | grep -i '^content-type')
  echo "$accept -> $code | $ctype"
done
```

```
text/turtle          -> 200 | content-type: text/turtle; charset=utf-8
application/ld+json  -> 200 | content-type: application/ld+json
text/html            -> 200 | content-type: text/html; charset=utf-8
application/rdf+xml  -> 200 | content-type: application/rdf+xml
```

**ทดสอบ security**

```
✅ UPDATE ถูกบล็อก        : 403 Forbidden
✅ query ไม่มี LIMIT       : เติม LIMIT 10000 อัตโนมัติ
✅ query ที่ใช้เวลานาน      : 408 Request Timeout
✅ ยิง 50 request ใน 1 นาที : 429 Too Many Requests
✅ Vary: Accept header    : มี
```

### Exercise 6 (โบนัส): เชื่อมกับ Wikidata

**โจทย์**

1. หา entity ใน dataset ของคุณที่น่าจะมีใน Wikidata (เช่น จังหวัด, ประเทศ, องค์กรใหญ่)
2. เขียนสคริปต์ที่:
   - ดึงชื่อ entity จาก graph ของคุณ
   - ใช้ **`VALUES` แบบ chunk** ค้นหาใน Wikidata (ไม่ยิงทีละตัว!)
   - สร้าง `owl:sameAs` link
   - ดึงข้อมูลเพิ่ม (ประชากร, พิกัด, ธงประจำจังหวัด) มาเสริม
3. วัดและรายงาน:
   - จำนวน HTTP request ที่ใช้
   - เวลาที่ใช้
   - อัตราการ match

**Expected output**

```
====================================================================
  ENTITY LINKING กับ WIKIDATA
====================================================================
  entity ที่ต้อง link : 77 จังหวัด
  chunk size         : 25
  HTTP requests      : 4        ← ไม่ใช่ 77!
  เวลา               : 6.3 วินาที

  ผลการ match:
    ✅ match ได้     : 74 (96.1%)
    ❌ ไม่พบ         : 2  (Bueng Kan, Nong Bua Lam Phu)
    ⚠️ ambiguous     : 1  (Chai Nat -- พบ 2 entity)

  ข้อมูลที่ดึงมาเสริม:
    population       : 74 จังหวัด
    coordinates      : 74 จังหวัด
    flag image       : 71 จังหวัด

  เพิ่ม 296 triples เข้า graph
```

พร้อมย่อหน้าอธิบายว่า **จัดการกรณี ambiguous อย่างไร** และ **ทำไมจึงไม่ควรใช้ `owl:sameAs` เมื่อไม่แน่ใจ**
(อ้าง [05.05](../05-knowledge-management/05.05-abox-negation.md) เรื่อง sameAs explosion)

## เกณฑ์ตรวจ

| Exercise | ผ่านเมื่อ |
| --- | --- |
| 1 | dataset ≥ 200 แถว, ≥ 6 คอลัมน์, รายงาน profile ครบ |
| 2 | reuse vocabulary มาตรฐาน ≥ 3 ตัว, IRI มาจาก business key |

| 6 | HTTP request ≤ ⌈N/chunk_size⌉, รายงานอัตรา match ได้ |

## Key Points

- Exercise 1–3 ฝึก **ETL pipeline กับข้อมูลจริงที่ไม่สะอาด** — ต่างจากตัวอย่างในบทเรียนโดยสิ้นเชิง
- **SHACL เป็น gate** — ต้องเจอ violation จริงจากข้อมูลจริง แล้วแก้ที่ต้นทาง
- Exercise 4 ตอกย้ำว่า **`rdf:type` สร้าง hub ปลอม** และต้องกรองออกก่อนวิเคราะห์เส้นทาง
- Exercise 5 ฝึกสร้าง **Linked Data service ที่ถูกต้องตามหลัก** รวมถึง security ที่มักถูกลืม
- Exercise 6 ฝึก **entity linking แบบมีประสิทธิภาพ** ด้วย `VALUES` + chunking
- ⚠️ **อย่าใช้ `owl:sameAs` เมื่อไม่แน่ใจ** — ใช้ `skos:closeMatch` แทนเพื่อเลี่ยง sameAs explosion
- เก็บ dataset และ ontology จาก Exercise ทั้งหมดไว้ เพราะจะนำไปใช้ต่อใน [Chapter 12](../12-linked-open-data/12.12-exercises.md)
