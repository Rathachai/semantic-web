# 10.12 แบบฝึกหัดบทที่ 10

แบบฝึกหัดชุดนี้ให้ออกแบบ ontology จริงตั้งแต่ competency questions จนถึงการประเมินผล
ทุกข้อทำต่อยอดกันได้ — ข้อ 1 สร้าง requirement, ข้อ 2–4 สร้าง ontology, ข้อ 5 ประเมิน

### Exercise 1: Competency Questions และขอบเขต

**โจทย์**: โรงพยาบาลต้องการ ontology สำหรับติดตามการนัดหมายและใบสั่งยา

จงเขียน
1. **Competency questions อย่างน้อย 8 ข้อ** พร้อมระบุว่าข้อไหนเป็น *factual*, *aggregate*, หรือ *inferential*
2. **ขอบเขต** — สิ่งที่อยู่ในขอบเขต (in-scope) และไม่อยู่ (out-of-scope) อย่างละ 5 รายการ
3. **SPARQL query โครงร่าง** สำหรับ CQ 3 ข้อแรก (เขียนได้แม้ยังไม่มี ontology)
4. **Negative test 2 ข้อ** — สิ่งที่ reasoner **ต้องไม่**อนุมาน

**Expected output**

```
CQ01 (factual)     : Which patients have an appointment with a given doctor?
CQ02 (factual)     : What medications were prescribed to a given patient?
CQ03 (aggregate)   : How many appointments did each doctor have last month?
CQ04 (inferential) : Which patients are high-risk (3+ chronic conditions)?
...

IN-SCOPE               OUT-OF-SCOPE
- Patient              - Billing / insurance claims
- Doctor, Nurse        - Hospital building layout
- Appointment          - Staff payroll
- Prescription         - Medical imaging files
- Diagnosis            - Clinical trial protocols

NEG01: ผู้ป่วยต้องไม่ถูกจัดเป็น Doctor แม้จะมี appointment
NEG02: ยาที่ถูกยกเลิกต้องไม่ปรากฏใน ActivePrescription
```

<details>
<summary>💡 คำใบ้</summary>

- CQ ที่ดีต้อง**แปลงเป็น SPARQL ได้** — "ระบบดีแค่ไหน" ไม่ใช่ CQ
- CQ แบบ *inferential* คือข้อที่ต้องใช้ reasoner ไม่ใช่แค่ query ตรง ๆ
- ทบทวน [10.02](10.02-competency-questions.md)

</details>

### Exercise 2: Conceptualization → Formalization

**โจทย์**: จาก CQ ในข้อ 1 จงสร้าง

1. **Glossary** อย่างน้อย 10 term พร้อมนิยามภาษาอังกฤษ
2. **Class hierarchy** (ลึก 3–5 ระดับ)
3. **Relation table**: property, domain, range, characteristics
4. **Attribute table**: property, domain, datatype, cardinality
5. แปลงเป็น **OWL (Turtle)** โดยระบุชัดว่า class ไหนเป็น *primitive* และ class ไหนเป็น *defined*

**Expected output** (บางส่วน)

```turtle
@prefix med:  <http://example.org/medical#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

# --- PRIMITIVE: เงื่อนไขจำเป็น (necessary) ---
med:Patient a owl:Class ;
    rdfs:subClassOf med:Person ;
    rdfs:label   "Patient"@en ;
    rdfs:comment "A person receiving medical care."@en .

# --- DEFINED: เงื่อนไขเพียงพอ (sufficient) ---
med:HighRiskPatient a owl:Class ;
    rdfs:label "High-Risk Patient"@en ;
    owl:equivalentClass [
        a owl:Class ;
        owl:intersectionOf (
            med:Patient
            [ a owl:Restriction ;
              owl:onProperty med:hasDiagnosis ;
              owl:onClass    med:ChronicCondition ;
              owl:minQualifiedCardinality "3"^^xsd:nonNegativeInteger ]
        )
    ] .
```

พร้อมตารางสรุป

```
CLASS                 TYPE       เหตุผล
Patient               primitive  ไม่มีเงื่อนไขที่บอกได้ว่าใครเป็นผู้ป่วย
Doctor                primitive  ต้องมีใบอนุญาต -- ตรวจจากข้อมูลอย่างเดียวไม่ได้
HighRiskPatient       defined    มี chronic condition ≥3 = เพียงพอเสมอ
ActivePrescription    defined    ยังไม่หมดอายุและไม่ถูกยกเลิก = เพียงพอ
```

<details>
<summary>💡 คำใบ้</summary>

- คำถามทดสอบ: *"ถ้ามีสิ่งหนึ่งที่มีคุณสมบัติครบตามที่ระบุ มันจะเป็น class นี้เสมอหรือไม่ — ไม่มีข้อยกเว้นเลย?"*
- ถ้าตอบ "ใช่" → **defined** (`owl:equivalentClass`)
- ถ้าตอบ "ไม่เสมอไป" → **primitive** (`rdfs:subClassOf`)
- ทบทวน [10.03](10.03-conceptualization.md) และ [10.04](10.04-formalization.md)

</details>

### Exercise 3: ใช้ Design Pattern แก้ปัญหาจริง

**โจทย์**: ontology ต่อไปนี้มีปัญหา จงระบุ **anti-pattern** ที่พบและแก้ด้วย **ODP** ที่เหมาะสม

```turtle
@prefix med:  <http://example.org/medical#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

# --- ปัญหา A ---
med:Doctor  a owl:Class ; rdfs:subClassOf med:Person .
med:Patient a owl:Class ; rdfs:subClassOf med:Person .
med:Doctor owl:disjointWith med:Patient .

# --- ปัญหา B ---
med:prescribedTo a owl:ObjectProperty ;
    rdfs:domain med:Medication ;
    rdfs:range  med:Patient .
med:aspirin med:prescribedTo med:john .    # เมื่อไหร่? ขนาดเท่าไหร่? กี่วัน?

# --- ปัญหา C ---
med:john med:allergies    "penicillin, sulfa, latex" ;
         med:doctorName   "Dr. Smith" ;
         med:department    "Cardiology" .

# --- ปัญหา D ---
med:DiabetesType1 a owl:Class ; rdfs:subClassOf med:Disease .
med:DiabetesType1 a med:DiseaseCategory .
```

จงส่ง
1. ระบุ anti-pattern ของแต่ละปัญหา (A–D) พร้อมอธิบายผลเสีย
2. Turtle ที่แก้แล้ว **ทั้งแบบ full form และ shorthand** สำหรับปัญหา B
3. SPARQL ที่ตอบคำถาม *"john ได้รับยาอะไรบ้าง ขนาดเท่าไหร่ ช่วงไหน"* หลังแก้แล้ว

**Expected output**

```
A → Role as Class
    Doctor ที่ป่วยเองจะทำให้ ontology inconsistent
    แก้: AgentRole pattern (Person + AgentRole + Role)

B → Binary relation ที่ควรเป็น Time-Indexed Situation
    เก็บขนาดยา วันที่เริ่ม-สิ้นสุดไม่ได้
    แก้: reify เป็น med:Prescription

C → String Everywhere
    allergies เก็บ 3 ค่าใน string เดียว, doctorName เชื่อมกับ med:drSmith ไม่ได้
    แก้: ใช้ IRI

D → Class as Instance (metaclass confusion)
    หลุดจาก OWL DL -- HermiT ปฏิเสธ
    แก้: แยก med:diabetesType1Category (instance) ออกจาก med:DiabetesType1 (class)
```

<details>
<summary>💡 คำใบ้</summary>

- ปัญหา B ต้องมี IRI แบบ composite key: `med:prescription/john-aspirin-2025-01`
- อย่าลืมเก็บ **shortcut property** คู่กัน หรือใช้ `owl:propertyChainAxiom`
- ทบทวน [10.05](10.05-odp.md) และ [10.06](10.06-anti-patterns.md)

</details>

### Exercise 4: Modularization

**โจทย์**: ontology โรงพยาบาลโตขึ้นเป็น 180 class จงแบ่งเป็น module

จงส่ง
1. **แผนภาพ module** พร้อมทิศทางการ import (ต้องเป็น DAG)
2. ไฟล์ **`med-core.ttl`** ที่มี `owl:Ontology`, `owl:versionIRI`, metadata ครบ
3. ไฟล์ **`catalog-v001.xml`** สำหรับ resolve IRI เป็นไฟล์ในเครื่อง
4. รัน [`code/ch10/check_modules.py`](../code/ch10/check_modules.py) กับ module ของตัวเองแล้วแสดงผล
5. อธิบายว่าถ้า `med-clinical.ttl` import `med-pharmacy.ttl` **และกลับกัน** จะเกิดอะไรขึ้น

**Expected output**

```
==================================================================
  MODULE CHECK
==================================================================

  Dependencies:
    core         → (none)
    clinical     → ['core']
    pharmacy     → ['core']
    scheduling   → ['core', 'clinical']

  Cycle check:
    ✅ ไม่มี cycle (เป็น DAG)

  Undeclared cross-module usage:
    ✅ ไม่พบ
```

และเมื่อสร้าง cycle จงใจ

```
  Cycle check:
    ❌ cycle: clinical → pharmacy → clinical
```

<details>
<summary>💡 คำใบ้</summary>

- โครงสร้างที่แนะนำ: `core` (Person, Organization, Document) → `clinical` / `pharmacy` / `scheduling`
- `owl:imports` ใช้ **ontology IRI** ไม่ใช่ path ของไฟล์ — จึงต้องมี catalog
- ทบทวน [10.07](10.07-modularization.md)

</details>

### Exercise 5: Evaluation ครบ 5 มิติ

**โจทย์**: จงประเมิน ontology ที่สร้างในข้อ 2–4 ครบทั้ง 5 มิติ

จงส่ง
1. **Consistency**: ผลการรัน HermiT + รายชื่อ unsatisfiable class (ถ้ามี)
2. **Completeness**: ผล CQ coverage test — ต้องได้ 100% ถ้าไม่ถึงให้อธิบายว่าขาดอะไร
3. **Conciseness**: ผลจาก [`code/ch10/ontology_eval.py`](../code/ch10/ontology_eval.py) พร้อมตีความทุกบรรทัดที่ขึ้น ⚠️
4. **Correctness**: verbalization อย่างน้อย 10 ประโยค พร้อมระบุว่าประโยคไหน domain expert น่าจะตอบว่า "ไม่จริง"
5. **Usability**: checklist ว่ามี label, comment, license, versionIRI, preferredNamespacePrefix ครบหรือไม่

**Expected output**

```
==================================================================
  METRICS: ontology/med-core.ttl
==================================================================
     triples              312
     classes               28
     objectProps           19
     dataProps             11
  ✅ cls/prop            0.93
  ✅ avgDepth            3.40
  ✅ avgBranching        2.80
  ✅ labelCov           100.0
  ⚠️  commentCov          38.2   ← entity หลายตัวไม่มี comment
  ✅ definedPct          21.4
     disjointPairs         15
  ✅ orphanPct           10.7

==================================================================
  VERBALIZATION -- ให้ domain expert ตอบว่า จริง / เท็จ
==================================================================
  [ ] Every Patient is a Person.                             ← จริง
  [ ] Nothing can be both a Doctor and a Patient.            ← เท็จ! หมอก็ป่วยได้
  [ ] Anything has at most one value for 'hasPrimaryDoctor'. ← ต้องถาม domain expert
  [ ] Anything that 'prescribes' something is a Doctor.      ← เท็จ! nurse practitioner ก็สั่งยาได้

USABILITY CHECKLIST
  ✅ rdfs:label ครบ 100%
  ⚠️  rdfs:comment 38.2% (ต่ำกว่าเกณฑ์ 50%)
  ✅ dcterms:license
```

<summary>💡 คำใบ้</summary>

- ประโยค verbalization ที่ domain expert ตอบว่า "ไม่จริง" **แต่ละประโยค = axiom หนึ่งข้อที่ต้องแก้**
- `rdfs:domain` ที่ทำให้เกิดประโยค *"Anything that X something is a Y"* คือกับดัก AP3 — ควรย้ายไป SHACL
- ทบทวน [10.08](10.08-evaluation.md)

## 🏆 Challenge: CQ-driven Development เต็มรูปแบบ

**โจทย์**: เขียนสคริปต์ Python ที่ทำครบวงจรแบบ [`code/ch10/cq_to_sparql.py`](../code/ch10/cq_to_sparql.py)
สำหรับ ontology โรงพยาบาล โดยต้อง

1. มี CQ อย่างน้อย 6 ข้อ พร้อม SPARQL test และ `expect_min`
2. `build_tbox()` สร้าง class อย่างน้อย 12 ตัว โดยมี **defined class ≥ 3 ตัว**
3. `build_abox()` สร้างข้อมูลตัวอย่างที่ทำให้ CQ ทุกข้อผ่าน — **อย่าลืม `owl:AllDifferent`**
4. รัน owlrl แล้วรายงานว่า CQ ข้อไหนผ่านเพิ่ม
5. ถ้ามี CQ ที่ owlrl ทำไม่ได้ ให้สลับไป HermiT แล้วแสดงผลเทียบกัน
6. Serialize TBox เป็น Turtle แล้วรัน `ontology_eval.py` กับผลลัพธ์

**Expected output**

```
  TBox 142 + ABox 87 = 229 triples

  --- ก่อน reasoning ---
  Coverage: 3/6 (50%)

  หลัง reasoning: 891 triples

  --- หลัง reasoning (owlrl / OWL 2 RL) ---
  Coverage: 5/6 (83%)

  ⚠️ CQ04 ยังไม่ผ่าน -- minQualifiedCardinality อยู่นอก OWL 2 RL
     ลองใช้ HermiT (OWL 2 DL) แทน:
  HermiT → HighRiskPatient: ['john', 'mary']

  ✅ Coverage สุดท้าย: 6/6 (100%)
```

<details>
<summary>💡 คำใบ้</summary>

**ข้อควรระวังจาก [10.10](10.10-python-design.md)**

| กับดัก | ทางแก้ |
| --- | --- |
| `xsd:date` ทำ HermiT พัง | ใช้ `xsd:dateTime` |
| ไม่มี UNA → cardinality ไม่ทำงาน | `owl:AllDifferent` + `owl:distinctMembers` |
| owlrl ทำ min cardinality ไม่ได้ | สลับไป HermiT |
| owlready2 อ่าน Turtle ไม่ได้ | `serialize(format="xml")` |
| owlready2 ออกเน็ตแล้ว 403 | `g.remove((None, OWL.imports, None))` |
| `EX.term` คืน bound method | ใช้ `EX["term"]` |

**สร้าง defined class ด้วย rdflib**

```python
from rdflib.collection import Collection

restr = BNode()
g.add((restr, RDF.type, OWL.Restriction))
g.add((restr, OWL.onProperty, MED.hasDiagnosis))
g.add((restr, OWL.onClass, MED.ChronicCondition))
g.add((restr, OWL.minQualifiedCardinality,
       Literal(3, datatype=XSD.nonNegativeInteger)))

inter = BNode()
members = BNode()
Collection(g, members, [MED.Patient, restr])
g.add((inter, RDF.type, OWL.Class))
g.add((inter, OWL.intersectionOf, members))
g.add((MED.HighRiskPatient, OWL.equivalentClass, inter))
```

</details>

## Key Points

- แบบฝึกหัดเดินตาม workflow จริง: **CQ → conceptualization → formalization → ODP → module → evaluation**
- **CQ ที่แปลงเป็น SPARQL ไม่ได้ ไม่ใช่ CQ** — เป็นความปรารถนา
- คำถามทดสอบ primitive/defined: *"มีคุณสมบัติครบแล้วเป็น class นี้เสมอหรือไม่"*
- Anti-pattern ที่เจอบ่อยที่สุดในโจทย์: **Role as Class**, **String Everywhere**, **Class as Instance**
- **`owl:imports` ต้องเป็น DAG** — cycle ทำให้ tool วนไม่รู้จบ
- Verbalization ที่ domain expert ตอบว่า "ไม่จริง" **แต่ละประโยคคือ axiom ที่ต้องแก้**
- ⚠️ อย่าลืม **`owl:AllDifferent`** ก่อนใช้ cardinality และ **`xsd:dateTime`** แทน `xsd:date`
- ถ้า CQ ต้องการ cardinality → **owlrl ทำไม่ได้ ต้องใช้ HermiT**
